Connector bars and the energy-trace chip **self-correct** — both measure live rects under `useConnectorLayout`'s `ResizeObserver` (verified: 20 bars, 4 active trace bars, hover-expand 158→208px after the resize). The two that do **not** self-correct, both in `TalentSurface.tsx` and both re-measured rather than scaled arithmetically: the bottom-row hover reserve `marginBottom` 160 → **220** (worst real bottom-row talent is cell 4-1, un-clamped at `scale(1.05)` = 363px against a 158px resting cell = 205px overshoot, was 148.1px) and the loading skeleton `minHeight` 908 → **1192** (measured tree-card box; keeps the skeleton→tree swap free of layout shift). 3 tiers fit without scrolling at 1440×900, 5 at 2560×1440. **Line clamp — fixed, and the clamp must stay on the inner span.** `.body`'s clamp was inert for the life of the component. The cause was **not** Lightning CSS (an earlier note here blamed it; the emitted chunk carries the declaration verbatim — that diagnosis was wrong). The real cause: `.body`'s only direct child is `RichText`'s single wrapping `<span>`, and `-webkit-box` lays out *children* as boxes — with exactly one child box there is nothing for `-webkit-line-clamp` to cut at, so the declaration computes (Chromium blockifies it to `display: flow-root`) but never bounds the height. Live-measured pre-fix on the Scout tree: Bolster `scrollHeight 194` vs `clientHeight 106`, hard-clipped mid-word. Short descriptions simply never reached the ceiling, which is why some plaques looked fine and others cut mid-word — **nothing was clamping anywhere**. Fix: `.body` becomes a plain `display: block; overflow: hidden` box (keeping `flex: 1`, so plaque geometry is unchanged) and the clamp moves to `.body > span` at **4 lines**. Standard `line-clamp` was tested and does **not** work here (the box just grew to fit all content), so the `-webkit-` form is required. The hover release also had to move: `.plaque:hover .body > span { display: block; -webkit-line-clamp: unset }` — `display: block` is what actually drops the `-webkit-box` line-boxing; `-webkit-line-clamp: unset` alone would not. Verified across the talents route (20 plaques, all states), the Force power tree, and the SpecSelectorList preview: max 4 lines everywhere, no text escaping any plaque, plain-text and inline-markup descriptions clamping identically. Native clamping truncates at *character* granularity, so the ellipsis can land inside a word (`…Decreas…`) — accepted deliberately, consistent with every other clamp in the app; word-boundary truncation would require per-plaque JS measurement. **`.fc-fx-desc` (globals.css) had the identical defect** — measured `scrollHeight 270` vs `clientHeight 32` — and was fixed the same way, including its `.fc-fx-row.is-expanded` release. `.fc-pow-desc.is-clamped` shares the structure and is very likely inert too, but its content fit its box in every case reachable, so it is unproven and left alone; `.ptt-name` wraps plain text and is expected to work, unverified. Mega-header (career line → title → ghost watermark → meta row) plays a once-per-route-load GSAP stagger reveal on first paint (Prompt 9, guarded by a `useRef` flag keyed off `shellReady`, not re-fired by later re-renders) — the four refs were **re-pointed** to the command bar's career line / title / skills row and the stage's watermark, with beat count, duration (0.3s), stagger (0.09s) and reduced-motion gating all unchanged; live-sampled at 14 partial frames with the original career→title→skills ordering intact. ## Custom Hooks (`src/hooks/`)

### `useCharacterData(characterId)`
**Owner of all character state.** The most important hook.

- Fetches and owns: character, skills, talents, specializations, force abilities, weapons, armor, gear, critical injuries
- Exposes computed stats: `forceRating`, `encumbranceCurrent`, `encumbranceThreshold`, `encumbranceStats`
  - **Encumbrance (Prompt 2 of The Archive, migration 125)**: single source of truth is now `computeEncumbranceStats()` in `src/lib/derivedStats.ts` — a pure function (no Supabase, no React) called from here AND from `LootAwardModal.tsx`, `MobileHudLayout.tsx`, `MobileSessionCompanion.tsx`. Replaces three inline `useMemo`s that used to live in this hook (`encumbranceCurrent`, `encumbranceBonus`, `encumbranceBonusSources`) — the per-item attribution `encumbranceBonusSources` gave is superseded by `encumbranceStats.capacitySources`, with suppressed/reason fidelity that array never had. Returns `{ base, wornCapacity, load, threshold, cliff, perItem, capacitySources, loadSources }` — `base = 5 + Brawn` computed live (not `characters.encumbrance_threshold`, which is only ever set once at character creation and can drift stale if Brawn is later raised — found one live case, Grevi Unduli, stored at 7 vs live-computed 8; the formula change intentionally corrects this). `threshold = base + wornCapacity`, `cliff = threshold + Brawn` (RAW: encumbered ≥ Brawn ⇒ no free maneuver, 2 strain/maneuver). Two worn-rules exclusivity checks, keyed on the new `ref_armor`/`ref_gear.worn_anchor` column: **Rule A** — equipped armor's own −3 encumbrance reduction (floor 0) applies only to the first equipped suit per `worn_anchor` (deterministic tie-break: ascending by item `id`, since no `equipped_at` timestamp exists in the schema); a second suit on the same anchor pays full cost, `reason: 'anchor_occupied_armor'`. **Rule B** — `encumbrance_bonus` counts only for the first equipped item (armor or gear) per `worn_anchor`; a duplicate grants +0, `reason: 'anchor_occupied_capacity'`, and still pays its own encumbrance. Both rules WARN, never block (item stays equipped); an armor item can be suppressed by both rules at once (verified via a synthetic two-Katarn-suits test). Items with no `worn_anchor` keep the old no-exclusivity behavior. **`is_dropped` fix**: `derivedStats.ts`'s pre-existing implementation already excluded `is_dropped` rows; the hook's inline version didn't — found as drift during the Task 1 audit. In practice this was unreachable (both the initial fetch in `characterDataPrefetch.ts` and every drop handler already filter/remove dropped rows before either function ever saw them), so the unified function's defensive check is parity/safety, not an observed live bug fix — documented separately per the prompt's instruction, not folded silently into "consolidated encumbrance."
- `handleSetEquipState`/`handleToggleWeaponEquipped`/`handleToggleEquippedById` (equip/carry/stow write path) now read-fresh-then-write, queued per row via a `Map<id, Promise>` chain (`enqueueRowWrite`) rather than deriving next-state from local React state and firing a last-write-wins update — rapid toggling or hover-preview on the same row now serializes instead of racing. Local state still updates optimistically, but only after the DB round trip, not before.
  - `forceRating` = `ref_careers.force_rating` (0 for every respec career as of migration 094 — careers no longer grant Force Rating) + owned `FORCERAT` talent ranks + (`characters.force_rating_purchased ? 1 : 0`). Owning a Force-sensitive specialization no longer contributes directly — see `isEligibleForForceRating` in `src/lib/forceEligibility.ts`.
  - `careerForceRatingBase` is also exposed (career contribution only, excluding FORCERAT/purchase) — passed to `computeDerivedStats` so `force_rating_conditional` talents (e.g. WITCHCRAFT) gate correctly against "does the career already grant a free Force Rating" rather than against the combined total, letting Witchcraft's bonus stack with the FORCERAT talent and the deliberate purchase instead of being zeroed by them. Example: a Mystic (career FR 0 under reSpec) with both the Witchcraft talent and one FORCERAT rank has Force Rating 2 — each contributes independently.
  - `derivedForceRating` (internal) re-runs `computeDerivedStats` to fold in talent modifier bonuses and write-backs `characters.force_rating` (the display cache) whenever it drifts — lives here rather than in a single UI component so both desktop and mobile keep the cache fresh for GM-side consumers that read the raw column.
- Exposes HUD transforms: `speciesAbilities`, `hudSkills` (`HudSkill[]`), `hudTalents` (`HudTalent[]`), `hudWeapons` (`WpnDisplay[]`), `hudArmor` (`ArmDisplay[]`), `hudGear` (`GearRow[]`)
- Exposes all mutation handlers: `handleSetEquipState`, `handleUpdateCharacter`, `handleAddWeapon`, etc.
- `handlePurchaseForceRating()` — deliberate 10 XP purchase of Force Rating 1 (sets `force_rating_purchased`); refuses if already purchased, XP < 10, or `!isEligibleForForceRating(...)` (includes the droid/clone lockout). `handlePurchaseForceAbility` now also refuses (at the handler level) when `forceRating < 1`. `handleBuySpecialization` refuses buying a Force-sensitive spec for droid/clone characters, and sets `pendingForceRatingOffer` (exposed with its setter) after a Force-sensitive spec purchase completes when the character is newly eligible at Force Rating 0.
- Realtime: Subscribes to `characters`, `character_weapons`, `character_armor`, `character_gear`, `character_skills`, `character_talents`, `character_critical_injuries`
- HUD display types (`HudSkill`, `HudTalent`, `WpnDisplay`, `ArmDisplay`, `GearRow`) live in `src/lib/types.ts`; panel files re-export them for backward compat

### `useGroupAssets(campaignId)`
- Fetches `group_assets` table — vehicles, starships, safe houses, strategic assets, NPCs, other
- Used by GroupSheet, GM dashboard, and PlayerHUDDesktop (for stow locations)
- Realtime: subscribes to `group_assets` channel

### `useGroupStorage(assetId)`
- Fetches stowed inventory for a single `group_assets` record marked `is_group_storage = true`
- Queries `character_weapons`, `character_armor`, `character_gear` in parallel filtered by `stow_location_id = assetId + equip_state='stowed' + NOT is_dropped`
- Returns: `{ items: GroupStorageItem[], loading: boolean, taking: Set<string>, takeItem }`
- `taking` is a `Set<string>` of item IDs currently being taken (per-item spinner)
- `takeItem(itemId, itemType, takerId, qty?)` → calls `take_group_storage_item` RPC; throws `Error` on failure
- Realtime: subscribes to INSERT/UPDATE/DELETE on all three item tables filtered by `stow_location_id`
- Pass `null` to disable fetching (used to pause when storage sheet is closed)

### `useCampaignPlayers(campaignId)`
- Fetches all players and their characters for a campaign
- Used by GM dashboard to populate initiative and combat panels
- Realtime: subscribes to `players` channel

### `useEncounterState(campaignId)`
- Tracks active encounter: `is_active`, `round`, `current_turn`, `tokens`, `initiative_order`
- Reads/writes `encounters` + `encounter_tokens` tables
- Realtime: subscribes to `encounters` channel
- Used by CombatPanel (GM side) and PlayerHUDDesktop (player side for combat status)

### `useQuartermaster(supabase, campaignId)`
- Owns all Quartermaster state for a campaign
- State: `qm: Quartermaster | null`, `qmItems: QuartermasterItem[]`, `buyRows: QmBuyRow[]`, `loading`
- Exposes: `toggleOpen`, `upsertItem`, `removeItem`, `getQmEntry`, `buyItem`, `sellItem`
- Realtime: subscribes to `quartermaster` (filtered by `campaign_id`) and `quartermaster_items` channels
- Used by `GroupSheet` (player QM button) and `QuartermasterModal` (full buy/sell UI)

### `useDestinyPool(campaignId, characterId, characterName, supabase)`
- Owns all Destiny Pool state extracted from `PlayerHUDDesktop`
- State: `destinyPool`, `pendingSpend`, `destinyPoolRecord`, `destinyRollRequest`, `destinySpendOpen`, `destinyGmFlash`, `destinyConsidering`
- Exposes setters for state that the parent component drives externally: `setDestinyRollRequest`, `setDestinySpendOpen`, `setDestinyGmFlash`, `setDestinyConsidering`
- Exposes `handleSpendDestiny(idx)` — two-tap confirm flow, persists to `campaigns.settings.destiny_pool`
- Realtime: subscribes to `campaigns` (postgres_changes), `campaign-events-*` (broadcast), `destiny-pool-player-*` (postgres_changes), `destiny-*` (broadcast)

### `useGmDestinyPool({ campaignId, campaign, characters, sendToChar })`
- GM-side Destiny Pool state extracted from `gm/page.tsx` to fix Single Responsibility violation
- Creates its own Supabase client internally
- State: `destinyPool`, `destinyPoolRecord`, `destinyGenerateOpen`, `manualAdjustOpen`, `gmSpendConfirm`, `manualLight`, `manualDark`, `manualBusy`
- Exposes all setters including `setDestinyPool` and `setDestinyPoolRecord` (needed by the campaign loader and the DestinyGeneratePanel callback)
- Exposes handlers: `handleGmSpendDark`, `handleApplyManual`, `flipDestinyToken`, `addDestinyToken`, `removeDestinyToken`
- Realtime: subscribes to `destiny-pool-gm-*` (postgres_changes on `destiny_pool` table)

### `useSessionMode(campaignId)`
- Tracks the current session mode (`'exploration' | 'combat'`) and round number for the campaign
- State: `mode`, `round`, `transitionPending`, `prevMode`
- Realtime: subscribes to `campaigns` channel to detect mode transitions

### `useSessionRollState(campaignId)`
- Manages session Duty/Obligation roll state from `session_roll_state` table
- State: `duty_roll`, `duty_triggered`, `obligation_roll`, `obligation_triggered`, etc.

- Live feed of dice roll results from `roll_log` table for all characters in a campaign

### `useCharacterSigAbilities(characterId, careerKey)`
- Signature Abilities Phase 1: owns `ref_sig_abilities`/`ref_sig_ability_nodes` lookup + this character's `character_sig_ability_nodes` purchases
- Returns: `{ availableSigAbilities: SigAbility[], lockedAbilities: Record<string, LockedSigAbility>, purchasedNodes: CharacterSigAbilityNode[], hasUnlockedTier5: boolean, lockInAbility(sigAbilityKey, specSlot), purchaseNode(sigAbilityKey, node), loading }`
- `lockedAbilities` is keyed by spec slot (`specialization_key`) — a character can lock a different signature ability under each in-career specialization it owns
- `hasUnlockedTier5`: true if `character_talents.xp_cost = 25` exists under a specialization in `ref_careers.specialization_keys` for `careerKey`. **Note:** for the `respec` dataset, `ref_specializations.career_key` is always `NULL` (migration 064 seeds it that way) — in-career association must go through `ref_careers.specialization_keys`, not a join on `ref_specializations.career_key`. (`useCharacterData.ts`'s `handleBuySpecialization` still does the `ref_specializations.career_key` join and is therefore always treating specs as out-of-career for respec — pre-existing, unrelated to this feature, not fixed here.)
- `lockInAbility`/`purchaseNode` are optimistic (local state updates before the Supabase write) and both deduct XP via a read-then-write on `characters.xp_available` (same non-atomic pattern `useCharacterData.ts` uses elsewhere)
- Realtime: subscribes to INSERT on `character_sig_ability_nodes` filtered by `character_id`
- Wired into both `useCharacterData` (exposed as `sigAbilities`, `lockedSigAbilities`, `purchasedSigNodes`, `hasUnlockedTier5`, `lockInAbility`, `purchaseSigNode`, consumed by `PlayerHUDDesktop`) and `useTalentSurfaceData` (same shape, plus `sigLoading`, consumed directly by the `/character/[id]/talents` route) — the talents route no longer goes through `useCharacterData` at all (Prompt 7a)
- Internal fetch (Prompt 7a): the `ref_sig_ability_nodes` query and the `hasUnlockedTier5` count query run in parallel (`Promise.all`) rather than sequentially — they have no dependency on each other, only on the initial 4-query batch (`ref_sig_abilities`/`character_sig_ability_nodes`/`character_specializations`/`ref_careers`), which was a sequential-by-accident hop, not a genuine one
- `careerKey` only starts this hook's fetch once truthy — previously always arrived from `useCharacterData`'s full 26-query batch (`character?.career_key`); on the talents route it now arrives from `useTalentSurfaceData`'s much smaller shell batch instead, so sig queries fire much sooner in wall-clock time without any change to this hook's own code
- Prompt 7c: its `ref_careers` lookup (previously a narrow `.select('specialization_keys').eq('key', careerKey).maybeSingle()` query) now reads from `refDataCache.ts`'s cached `ref_careers` rows instead of its own network request — a warm cache serves this with zero additional queries

### `useTalentSurfaceData(characterId)`
- Lean, route-scoped data hook for `/character/[id]/talents` only (Prompt 7a) — replaces `useCharacterData` on that route. Fetches only what `TalentSurface` and the route's header/rail render: `characters`, `character_specializations` (the "shell" batch, plus cached ref data) and `character_talents` (the "tree" batch, plus cached `ref_talents`) — both batches fire in parallel, each exposing its own readiness flag (`shellReady`, `treeReady`) instead of one blocking `loading` boolean, so the route can paint the header/rail as soon as the shell resolves while the tree area shows its own local skeleton. Signature-ability data comes from `useCharacterSigAbilities`, unchanged.
- Does NOT fetch weapons/armor/gear/crits/species/force-abilities/item-descriptors/attachments/qualities/obligation-or-duty-types/character_skills — none of it renders on this route (was ~68% of `useCharacterData`'s payload on this route)
- Prompt 7c: `ref_specializations`/`ref_careers`/`ref_skills`/`ref_talents` now come from `refDataCache.ts`'s shared, dataset-keyed cache instead of this hook's own queries — on a warm cache (e.g. arriving from the sheet, which populates the same cache) this hook fires zero ref queries; only `characters`/`character_specializations`/`character_talents` remain as real per-navigation requests. The `ref_specializations` retired-spec fallback merge (`missingSpecKeys`) stays as this hook's own character-specific post-processing on top of the cached rows — it is not, and cannot be, part of the shared cache.
- Mutation handlers (`handlePurchaseTalent`, `handleRemoveTalent`, `handleResolveDedication`, `handleCancelDedication`, `handleBuySpecialization`) do not duplicate purchase/XP logic — they call the same standalone functions (`purchaseTalent`, `removeTalent`, `resolveDedication`, `cancelDedication`, `buySpecialization`, `applyTalentModifiers`) that `useCharacterData.ts` now exports and calls itself, each hook supplying its own state/setters via a `deps` bag. The XP-race-safe fresh-read-before-write pattern lives in exactly one place either way.
- `useCharacterData.ts` itself is otherwise unchanged in behaviour — its own `loadCharacter` fetch (used by `PlayerHUDDesktop`/`MobileHudLayout`/everything else) still fetches the same tables in the same shape; only its ref_skills/ref_talents/ref_specializations/ref_careers legs are now cache-backed (Prompt 7c) instead of firing their own queries every mount.

### `useDerivedStats(input)`
- Computes derived character stats: soak, encumbrance thresholds, wound/strain thresholds, XP spent, force rating
- Input: character + talents + armor + weapons + ref data + optional `moralitySystem` (`'vanilla' | 'force_presence'`, defaults `'vanilla'`)
- Extracted computation logic; complements `useCharacterData`
- Force Presence threshold bonuses (Prompt B): when `moralitySystem === 'force_presence'`, `character.dark_points >= 7` adds `+2` wound / `-2` strain, `light_points >= 7` adds `+2` strain (both simultaneously is impossible — `light+dark<=10` DB CHECK). Deliberately NOT folded into `mods.woundThresholdBonus`/`strainThresholdBonus` (`computeDerivedStats`, `derivedStats.ts`) — those accumulate talent bonuses that are separately, permanently written back to `character.wound_threshold`/`strain_threshold` by `applyTalentModifiers`, and `effectiveStats.woundThreshold`/`strainThreshold` read those DB columns directly rather than `mods` — so anything added only to `mods` would never reach `effectiveStats` at all. Force Presence bonuses instead get their own additive term, applied directly at `effectiveStats` assembly, with their own appended tooltip source entries — purely derived, never written back, unlike talent bonuses. `PlayerHUDDesktop.tsx` computes `derivedStats` once and passes the same `effectiveStats` to both `HudStatusStrip` and `HudForceTab`, so the two can't disagree. Mobile (`MobileHudLayout.tsx`/`MobileSessionCompanion.tsx`) doesn't thread `moralitySystem` — defaults to `'vanilla'`, no behavior change, out of scope for this prompt.

### `useMapTokens(mapId, options?)`
- Owns `map_tokens` table state for the active combat map
- State: `tokens: MapToken[]`; each token has position, participant type, label, wound pct, visibility
- Realtime: subscribes to INSERT/UPDATE/DELETE on `map_tokens` (table has `REPLICA IDENTITY FULL` so DELETE filter on `map_id` works correctly for external deletes by `slot_key`)
- `options.visibleOnly` (Prompt 11) — player-facing callers only (`PlayerHUDDesktop.tsx`, `/table/page.tsx`). Adds `.eq('is_visible', true)` to the initial fetch and drops/excludes hidden rows in the realtime INSERT/UPDATE handler, so hidden-token data no longer sits resident in the player client's React state (the old pattern fetched every row, hidden included, and only hid it via a client-side `.filter()` after the fact — inspectable in React state/devtools the whole time). This does **not** fully close the gap: `map_tokens` RLS is `USING (true)` (`032_maps.sql`), so Realtime itself still evaluates that permissive policy and could broadcast one hidden-row UPDATE payload in transit before this filters it client-side. Closing that needs an RLS policy change (a migration — out of scope for Prompt 11, flagged for follow-up). GM call sites (`GmMapView.tsx`, `GmShell.tsx`, `StagingLeftRail.tsx`) omit the option and keep seeing every token, hidden included, same as before.

### `useGmBroadcast(characters)`
- GM → player Supabase broadcast channel management
- Maintains per-character channels keyed by `character_id` (never destroys on re-render to avoid race)
- Exposes: `notify(charId, type, message)`, `sendToChar(charId, payload)`, `broadcastAll(payload, characters)`
- **Also exports two standalone (non-hook) `pending_actions` writers**, deliberately co-located with `sendToChar` because a GM action fires both: the broadcast is the instant delivery path, the queue row is the durable one.
  - `createPendingAction({ campaignId, characterId, actionType, payload?, sourceRef?, isBlocking? })` → `{ action, duplicate, error }`. Absorbs the `23505` raised by the partial unique index and returns the already-outstanding row with `duplicate: true` — re-firing a live request (GM pressing "Request Rolls" twice, or a per-card retry after a global request) is a no-op, not an error. Omitting `sourceRef` disables deduplication, since the index treats NULLs as distinct.
  - `cancelPendingAction(id)` — sets `status = 'cancelled'`, releasing the partial unique index so the same `source_ref` can be requested again. The durable counterpart to the existing `destiny-roll-cancel` broadcast, which only clears client state.
  - `cancelPendingActionsByType(campaignId, actionType, sourceRef?)` — campaign-wide sweep of every outstanding row of one type, optionally narrowed to one setup session. Exists for invalidation paths with no row ids in scope; `endEncounter` is the motivating case.
  - **Initiative is wired (see `InitiativeSetupModal` below). `DestinyGeneratePanel` is not** — that adoption is still pending.

### `usePendingActions(characterId, supabase)`
- Player-side view of this character's unresolved `pending_actions` rows (migration 117) — the durable substrate behind the planned Notifications drawer
- Returns: `{ actions: PendingAction[], count, blockingCount, resolve(id, resultPayload?) }`, ordered blocking-first then oldest-first
- Initial `SELECT` on `status = 'pending'` is the catch-up that broadcast-only delivery cannot do: today every decision popup arrives solely via `usePlayerBroadcast`'s `gm-action` channel, so a socket that is asleep or reconnecting silently drops the request and the player sees nothing (the suspected cause of the macOS Safari reports)
- Realtime: subscribes to INSERT/UPDATE/DELETE on `pending_actions` filtered by `character_id` (table is `REPLICA IDENTITY FULL`, so the filter holds on UPDATE/DELETE too); rows leaving `'pending'` drop out of the list. Subscription/cleanup shape follows `useCriticalInjuryRequest.ts`
- `resolve` is optimistic, writes `status = 'resolved'` + `resolved_at` + `result_payload`, and guards on `.eq('status','pending')`. `result_payload` carries the **actual result**, not merely a resolution flag — initiative values currently live only in `roll_log` (append-only, display) and in `InitiativeSetupModal`'s transient React state, so a GM reload loses them today
- Exports `PendingAction`, `PendingActionType`, `PendingActionStatus`
- Consumed by `InitiativeRollModal.tsx` (resolves its own row on submit) and by `PlayerHUDDesktop.tsx`, which feeds the Alerts button and the pending-action drawer (see `HudNotificationsDrawer` below).

### `useGmSession(campaignId, ...)`
- Owns combat session state: session mode transition, staging encounter, adversary/vehicle instances
- State: `sessionMode`, `combatRound`, `sessionBusy`, `stagingEncounter`, `stagingInitRoster`, `stagingVehicleRoster`, etc.
- Coordinates mode transitions between exploration and combat; triggers encounter creation in Supabase
- **Encounters are per-map and permanent (migration 115).** `stagingEncounter` is loaded by `(campaign_id, map_id)` on the active map, not by `is_active`, so switching maps swaps decks and the deck exists with or without combat. `is_active` now means only "combat is live on this row": `handleStagingCombatStart` sets it (updating the map's existing deck rather than inserting a row, merging the setup modal's edited rosters over the deck's by `instanceId` so entries left out of initiative survive as non-combatants), and `endEncounter` clears it plus `round`/`current_slot_index`/per-slot `acted`+`current`. `endEncounter` no longer deactivates the row or nulls `map_tokens.slot_key` campaign-wide — that pair was what emptied every map's deck and permanently unlinked surviving tokens from their instances when combat ended. Initiative slots carry no state between fights; Begin Combat regenerates them wholesale.
- `stagingAddToEncounter` (off-map add) creates the map's deck on demand via `ensureEncounterForMap` and toasts on success/failure, instead of silently early-returning when no combat had ever been started
- `stagingEncounter`/`setStagingEncounter` is the sole canonical `combat_encounters` subscription for the whole GM view (the old `useEncounterData` hook it might have overlapped with was dead code and has been deleted)
- Exposes `markEncounterPending`/`clearEncounterPending` — tracked in a `pendingKeysRef` set of `instanceId:stat` keys with an in-flight debounced write from `useEncounterCombatControls`
- Realtime merge is field-aware: incoming `combat_encounters` rows are staleness-checked against the last-applied `updated_at` (rejects out-of-order echoes), then merged per-instance — any adversary/vehicle instance with a pending key keeps its local (optimistic) version instead of the incoming row's, while everything else (initiative slots, other instances) takes the incoming row
- `beginCombat`, `changeRound`, `stagingLibrary`, `stagingLibraryLoaded`, `loadStagingLibrary` were removed (confirmed zero callers)
- `openStagingCombatModal` builds two parallel rosters from `map_tokens` for the "Begin Combat" flow: `stagingInitRoster` (adversary tokens, `participant_type==='adversary' && token_shape!=='rectangle'`) and `stagingVehicleRoster` (vehicle tokens, same `participant_type` but `token_shape==='rectangle'` — vehicles have no distinct `participant_type`). Adversary instances now carry `AdversaryInstance.alignment` (optional field on `src/lib/adversaries.ts`, threaded through `adversaryToInstance()`'s 3rd param), populated from the map token's stored `alignment` here — this is what lets `InitiativeSetupModal` show a genuine "Friendly NPC"/"Enemy" tag instead of defaulting everyone to enemy. `handleStagingCombatStart` wires `map_tokens.slot_key` for both adversary and vehicle tokens that ended up with a slot. `stagingAddVehicleToEncounter` (incremental single-vehicle mid-combat append) was removed as dead code — it had zero call sites and doesn't fit the batch client-side slot-building `InitiativeSetupModal` uses.
- `InitiativeSetupModal` (`src/components/dm/InitiativeSetupModal.tsx`) — **full-screen three-column GM panel** for "Begin Combat"/"Recheck Initiative" (was a stacked 4-step 760px modal; the stacked order list forced heavy scrolling, which drove the rework). Rendered via `Modal`'s `fullScreen` prop at `Z.hudSupreme` — `GmTopBar`/`GmLeftRail` sit on `--z-hud-combat` (9001), so the default modal layer would let the GM chrome overlap column 1 and the deck/FAB cover the Lock button. Header carries the Cool/Vigilance segmented control, which now sets the **default** skill for the whole encounter. Column 1 = one card per PC (roll-status chip, per-row skill selector, dice-pool pips, editable Succ/Adv, per-card `↻` that re-requests from that character only via `sendToChar`, alongside the global "Request Rolls"); values arriving from a player's broadcast render in the success colour with `data-live="true"` and revert to plain GM styling the moment the GM types over them. Column 2 = adversaries + vehicles. Column 3 = the compact sticky order rail + Lock Order & Start.
  - **Per-row skill assignment.** `ref_skills.type` is the category field — `stCombat` is exactly `BRAWL/GUNN/LTSABER/MELEE/RANGHVY/RANGLT` — so every skill selector (GM and player) filters `type !== 'stCombat'` rather than carrying a hardcoded exclusion list. The modal fetches the whole `ref_skills` catalog plus every PC's full `character_skills` row set (the old query filtered to `skill_key IN ('COOL','VIGIL')`); the `charSkillRanks` prop survives as a Cool/Vigilance seed. Adversary pools resolve `skillRanks` by **display name** (that's how `AdversaryInstance.skillRanks` is keyed) and the characteristic via `CHARACTERISTIC_ABBR`. The GM's per-row pick feeds that row's roll and rides along on the `initiative-request` broadcast as `skillKey`; a player's own pick arrives back on `initiative-result` as `skillKey`/`skillName`, clears any standing GM override for that character (the player's action is newer) and is flagged on the card. No persistence — all transient modal state, no migration.
  - **Visibility + exclusion.** Only adversaries whose live `map_tokens` row exists and has `is_visible` are listed; hidden and off-map (token-less) entries are merged into one `◌ N hidden token(s) — reveal on map to include` note and produce no slot. Tokens carry no instance id (`participant_id` is always null), so the bridge is `map_tokens.slot_key` → the deck's persisted `initiative_slots[].adversaryInstanceId`/`vehicleInstanceId`, with label matching as fallback; `tokens`/`encounterSlots` are passed in from `GmShell`. The same bridge fixes disposition: effective alignment is GM override → `AdversaryInstance.alignment` → token alignment → deck slot alignment → `'enemy'`, so the Recheck-initiative call site (whose roster predates the instance field) no longer silently shows every friendly NPC as Enemy. Per-card `✕` excludes (de-emphasised, restorable via `↥`, no slot); "Roll All Visible" skips excluded rows. Vehicles never roll — hand-entered Succ/Adv and the "own initiative slot" toggle only, no roll button and no skill selector.
  - **Pending-action queue wiring (migration 117).** Every player roll request now has two deliveries: the existing `sendToChar` broadcast (fast path) *and* a `pending_actions` row (durable path). Neither replaces the other — the broadcast is instant for a connected player, the row is what survives a suspended socket, which is the whole reason the queue exists.
    - **`source_ref` = a setup-session id**: a `useRef(randomUUID())` minted once per mount. `GmShell` renders the modal only while `initiativeSetupOpen` is true, so it is stable across one setup session and distinct across close-and-reopen — deliberate, since one encounter can legitimately need initiative twice. **Not** `stagingEncounter.id`, which is identical across both of those and absent on the recheck path. It is never null: a null `source_ref` would silently disable the partial unique index (NULLs are distinct in Postgres), which is the entire dedupe mechanism.
    - Both fire sites (`handleRequestRolls`'s loop and the per-card `↻`) route through `requestRollFor`, so the row creation is one code path. A repeat request collapses onto the existing row via `uq_pending_actions_open`; `createPendingAction` absorbs the `23505` and the GM sees nothing.
    - The modal subscribes to `pending_actions` (filtered on `campaign_id`, narrowed to its own `source_ref` client-side, since Realtime filters take one column). A row arriving `resolved` with a `result_payload` is folded into `pcResults`/`pcLive`/`pcPlayerSkill` exactly as the broadcast handler would have — this is what recovers a submission whose broadcast was dropped.
    - **The zero/zero ambiguity is fixed.** `pending: r.successes === 0 && r.advantages === 0` could not distinguish a genuine 0-success/0-advantage roll from an unanswered request. `pcIsPending(charId, r)` now reads the row's status first (`resolved` → rolled, `pending` → pending) and falls back to the old heuristic only when no row exists for that character in this session (a GM-rolled adversary, a vehicle, a duplicate, or a request predating the queue). Both consumers were updated — the `⏳ Pending`/`✓ Rolled` chip and `resolveBoardItem`'s rail score. Note `sortInitiative` never consumed the `pending` flag (it sorts on `successes`/`advantages`), and `allSlots`' own `pending` field has no reader; they were left as-is.
    - **Mount sweep.** On every mount the modal cancels *all* `pending` initiative rows for the campaign (`cancelPendingActionsByType(campaignId, 'initiative')` — no `sourceRef`) and broadcasts `initiative-cancel` to every character in the `characters` prop. This closes the GM-reload gap: a reload mints a new `setupSessionIdRef` and can no longer see the previous session's rows, which would otherwise sit `pending` until combat ended with a player still holding an orphaned roll modal. Campaign-wide by necessity — at mount there is no live session to distinguish a dead one from. Guarded by a `sweepStartedRef` so StrictMode's double-invoke and any re-render cannot re-fire it, and both request controls are disabled until `sweepDone`, so a request can never be created before the sweep that would cancel it lands. Resolved rows are untouched (the helper filters `status = 'pending'`).
      - **Explicitly not recovery.** Submitted rolls from the dead session are *not* adopted: no session id is persisted, `pcResults` still seeds to all-zero, and the GM re-requests, reading any prior values off the roll feed. A decision, not an oversight.
    - **`initiative-cancel`** — a new per-character message on the existing `gm-notify-<characterId>` channel, paired with `cancelPendingActionsByType`. Fired from four places (the mount sweep above, plus): modal close (`handleClose`, wrapping both the `✕` and `Modal`'s `onClose`), Lock Order & Start (`handleStart`), and `endEncounter` (`useGmSession.ts`). The first two scope by setup-session `source_ref`; `endEncounter` runs long after the modal is gone and sweeps by campaign. Before this, all three paths left an orphaned player roll modal open, broadcasting into a channel whose only subscriber had unmounted.
    - Inclusion rule: only entries in the `characters` prop produce a row. Adversaries are GM-rolled locally, vehicles are hand-entered, duplicates share the original's values, Reserve and excluded produce no slot — none of them can reach `requestRollFor`.
    - The **Recheck Initiative** instance is deliberately left unwired: `setRecheckInitiativeOpen(true)` is never called anywhere, so that modal is currently unreachable.
  - The order rail is a dnd-kit (`@dnd-kit/core`/`sortable`/`utilities` — first use in the codebase) sortable **dense single-line rail** — drag handle, position number, role colour dot, name, compact `2s·1a` score — with Duplicate (⧉, independently-draggable copy sharing the original's live roll values, no re-roll, badged `×N · Nth Action`) and Bench (✕, moves to a single collapsed Reserve row with a count badge) hover actions. Reserve is local/transient state, reset on every modal remount, with its own dnd-kit sortable list and a Restore (↥) action. The board auto-mirrors the roll-driven `sortInitiative()` order (`allSlots`) until the GM's first manual drag/duplicate/bench/restore (`boardTouched` flag), after which it's GM-authoritative; `handleStart` builds `finalSlots` from the live board order (not `allSlots` directly), so benched participants never reach `initiative_slots` and duplicates each get their own slot keyed by a local `boardId` (not any DB id). Role colours: gold=active/position-1, `var(--hud-accent-purple)`=PC, `var(--state-failure)`=enemy NPC, `var(--state-advantage)`=friendly NPC, `HUD.gold`+"VEH"=vehicle (matches `CombatFeedPanel`'s `TypeBadge`). Renders inline within the ambient theme (no theme forcing) — matches `InitiativeStrip`/`CombatFeedPanel`, both of which render inside GmShell's forced `gm-imperial` theme.
- `MapToolsRadial` (`src/app/gm/MapToolsRadial.tsx`) has a 4th arc, "Table Display" — a direct action (no popup panel) that opens `/table?campaign=<id>` in a new tab; restores the `⛶ Table Display` entry point lost when `GmMapPanel`'s Map section was gutted to token-only controls.

### `useEncounterCombatControls({ encounter, setEncounter, saveEncounter, supabase, campaignId, tokens, updateTokenWoundPct, markPending, clearPending, options? })`
- Shared write layer for all Encounter Deck card controls (`EncounterDeck.tsx`) — successor to the five combat adjustment functions previously inlined in the now-deleted `EncounterAdversaryPanel`/`EncounterVehiclePanel`

## Data Layer

### Supabase Tables (30+ tables, key ones)

**Characters & Skills**
- `characters` — base stat block, XP, credits, backstory
- `character_skills` — per-character skill rank overrides
- `character_talents` — purchased talents with tree position + xp_cost
- `character_specializations` — purchased specs, in purchase order
- `character_force_abilities` — purchased Force power upgrades
- `character_critical_injuries` — tracked injuries
- `character_sig_ability_nodes` — Signature Abilities Phase 1: purchased sig-ability tree nodes (base + upgrades). `spec_slot` (migration 090) records which `specialization_key` the ability was locked in against, since a character can lock a different signature ability per in-career spec. Cleanup via `useEffect` return → `supabase.removeChannel(channel)`.

### Modal ignition — the canonical check-panel open/close animation

Named convention, established by Combat Check and **intended for reuse by Skill Check and Force Check**. The modal visibly emanates from the button that launched it.

- **Helper, not a component.** `igniteModalOpen(targets)` / `igniteModalClose(targets)` in `src/lib/utils.ts`, plus `.fc-pulse` / `.fc-scrim-ignite` in `globals.css`. There is deliberately no `<IgniteModal>` wrapper, hook file or animation module — the caller owns its refs, its `usePrefersReducedMotion()` value and its effect lifecycle, and hands the elements over.
- **`IgniteTargets`**: `{ inner, scrim, pulse, origin, accent, glow, restShadow, reducedMotion }`. **Accent and glow are parameters** — nothing panel-specific is hardcoded, so each panel passes its own. `origin` is the triggering element; a missing node falls back to the viewport centre so the animation still plays, just without the spatial link.
- **Open (~450ms):** scrim fades 120ms from t=0 · radial pulse from the button's centre, scale 0.4→16, opacity 0.9→0 over 420ms `power2.out` from t=0 · ignition from t=40ms, inner `scale: 0.08 → 1` over 340ms `back.out(1.4)` with `transformOrigin` at the button expressed relative to the modal's own box, starting on a hot border (`0 0 60px <glow>, 0 0 0 2px <accent>`) that cools to the resting shadow over 280ms overlapping by 80ms · content stagger from t=160ms, `opacity 0→1, y 14→0`, 300ms each, 50ms stagger. Stagger targets are tagged `data-ignite-stagger` at any depth; DOM order is tray-first, which is correct.
- **Close (~300ms, always faster):** content out (120ms, 20ms stagger, `power2.in`) · inner collapses to `scale: 0.08, opacity: 0` toward the same origin (240ms `power3.in`, overlapping by 40ms) · scrim out (160ms, overlapping by 60ms). `IGNITE_EXIT_MS` (300) is what you feed to `Modal`'s `exitMs`.
- **Animate the inner wrapper only.** The positioned anchor holds `position: fixed` and the centring transform; GSAP must never touch it.
- **Never gates anything.** The state write happens first and independently; the timeline is decorative. If they ever disagree, the write wins.

**Canonical effect shape** (the well-behaved pattern already used by `PresenceFlash`, `HudNotificationsDrawer` and `TalentsPanel`, now codified):

```ts
const prefersReducedMotion = usePrefersReducedMotion()
const tlRef = useRef<gsap.core.Timeline | null>(null)
useEffect(() => {
  tlRef.current?.kill()                       // spam-safe: kill in-flight first
  tlRef.current = open ? igniteModalOpen({...}) : igniteModalClose({...})
  return () => { tlRef.current?.kill() }      // clean up on unmount
}, [open, prefersReducedMotion])              // hook is false on first render —
                                              // it MUST be a dependency
```

Reduced motion collapses to a plain opacity fade (120ms in, 100ms out): no pulse, no scale, no stagger.

> **Known debt, out of scope here:** roughly half the app's GSAP consumers predate this convention — `MapToolsRadial`, `EncounterDeck`, `EncounterDossier`, `PlayerTokenTooltip`, `PresenceSmoke` ignore `usePrefersReducedMotion()` entirely, and `EncounterDeck`, `EncounterDossier`, `PresenceSmoke`, `ForcePanel` never kill their timelines. Retrofitting them is a separate cleanup.

The height tween is added to the timeline **last with an explicit position (`0.1`)** so the cross-fade's own relative timings are untouched while the two read as one motion. Three consequences worth keeping straight:
  - `.fc-phase-abs` is `top/left/right: 0` with auto height, deliberately **not** `inset: 0`. A bottom-anchored phase is stretched to the wrapper's current height, so measuring it would report the wrapper back and the spring could never shrink.

That state is not merely cosmetic: it made the whole console 228px tall with the skill tiles unclickable underneath the tray and footer.
  - First run of a freshly-mounted console snaps the height (`phaseMountedRef`) instead of tweening `0 → full`, which would be a second motion competing with the ignition. Reduced motion snaps both the height and the swap.
- **Locked panels use `filter: opacity()`, never the `opacity` property** — the same conflict that bit the three-column form: GSAP writes inline `opacity` during the stagger and an inline style beats a class.
- `difficultyChosen` is **presentational** state: `selectedDifficulty` defaults to 2 (Average) and so cannot answer "has the player chosen yet".
- **Skill selection resets** Boost/Setback/upgrades/Force and returns difficulty to Average — pre-existing behaviour in `selectSkill`, deliberately preserved.

## State Management Pattern

Holocron uses **minimal global state** — Zustand stores for transient UI selections (e.g., selected character). Primary state flows as:

```
Hook (owns DB + realtime) → Page shell (owns display transforms) → Panel (pure display)
```

1. Hooks fetch from Supabase and expose raw DB rows + computed stats
2. Page shells (`PlayerHUDDesktop`, `gm/page.tsx`) do **all** the mapping into HUD-friendly display objects (`hudWeapons`, `hudSkills`, `hudGear`, etc.) via `useMemo`
3. Panels receive props and render — they call back up for mutations

**Mutation flow**: Panel calls prop callback → Page shell delegates to hook handler → Hook optimistically updates local state + writes to Supabase → Realtime subscription fires on other clients → All clients re-render

## Design Token System

**Source of truth**: `src/lib/tokens.ts`
```typescript
import { COLOR, HUD, FS, SP, RADIUS, Z, SHADOW, EASE, CHAR_COLOR, DICE_META, SYM } from '@/lib/tokens'
```

**Dice identity colours**: `DICE_COLOR` (fill) and `DICE_OUTLINE` (edge) in `tokens.ts` are the single source of truth — `components/dice/DiceFace.tsx` re-exports `DICE_COLOR` as `DICE_COLORS` rather than keeping its own copy (that duplicate is how setback drifted to a blue-grey indistinguishable from boost). Setback is the one die whose fill (`#0D0F12`, black) cannot double as its ink: it takes the light grey `DICE_OUTLINE.setback` for strokes/borders, and the `.die.setback` chip in `globals.css` pairs `--die-setback-fill` (body) with `--die-setback` (ink/edge). Any solid-shape die chip must draw the outline or the black die disappears against the HUD.

**Dice SHAPES are identity, exactly like dice colours — `DICE_META[type].shape` is the single source of truth and is not negotiable per-surface.** The FFG dice each have one physical shape and every renderer must draw it:

| `shape` | Dice | How to draw it |
|---|---|---|
| `octagon` | **Force**, Proficiency, Challenge | `clip-path: polygon(30% 0%,70% 0%,100% 30%,100% 70%,70% 100%,30% 100%,0% 70%,0% 30%)` — the `CLIP_OCT`/`CLIP_OCTAGON` constant duplicated in `CombatCheckOverlay.tsx`, `HudSkillQuickList.tsx` and `RangeBandStep.tsx` |
| `diamond` | Difficulty, Ability | `clip-path: polygon(50% 0%,100% 50%,50% 100%,0% 50%)` (`CLIP_DIA`) |
| `rounded` | Boost, Setback | `border-radius: RADIUS.sm` |

**A `border-radius` square is never a valid Force / Proficiency / Challenge die.** This regressed once — the Force Check console's rebuilt dice (`.fc-fdie`) shipped as 12px-rounded squares — so when adding any new die renderer, read `DICE_META[type].shape` rather than eyeballing it, and check the three existing `CLIP_*` constants first.

**Glow on a clipped die must be a wrapper `filter: drop-shadow`, not `box-shadow`.** `clip-path` clips `box-shadow` away entirely, so an outer halo declared on the clipped element itself renders as nothing; only `inset` shadows survive. The established fix is a plain wrapper element carrying `filter: drop-shadow(...)`, which follows the child's painted pixels around the octagon instead of its bounding rectangle — see `.fc-fdie-glow` in `globals.css` and the identical wrapper idiom in `HudSkillQuickList.tsx`'s tray dice.

**CSS custom properties**: `src/app/globals.css` defines `--color-gold`, `--font-rajdhani`, etc. using `clamp()` for fluid scaling.

**Theme-aware semantic CSS variables**: New opacity stops for HUD colors enable theme overrides via `[data-theme]` selectors without component changes:
- `--hud-accent-10`, `--hud-accent-20`, `--hud-accent-25`, `--hud-accent-35`, `--hud-accent-40`, `--hud-accent-45`, `--hud-accent-50`, `--hud-accent-60`, `--hud-accent-border`
- `--hud-gold-subtle`, `--hud-gold-border`, `--hud-gold-40`

**Faction image styling** (`.hud-fi` base class): 18×18px container with per-faction CSS filter chains applied via `.hud-fi-rebel`, `.hud-fi-jedi`, `.hud-fi-empire` classes; theme-specific overrides via `[data-theme="operative"]` and `[data-theme="kyber"]` selectors

**Rail button styling**: `.hud-rail-btn-*` classes for quick/nav/utility buttons; `.hud-rail-btn-adversaries` for red-tinted adversaries button

**Backward-compat shims**: `src/components/player-hud/design-tokens.ts`, `src/components/wireframe/wf-tokens.ts`, and `src/lib/styles.ts` re-export from `tokens.ts`. New code must import directly from `@/lib/tokens`.
